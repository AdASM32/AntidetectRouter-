# Виртуальный роутер Plus: PPTP

## Разбор исходного проекта

На момент анализа `AdASM32/AntidetectRouter-` и `vektort13/AntidetectRouter`
имеют одинаковый HEAD: `dad2dcc3ba3ba712219d17bd5651c6396b2ad899`.
Основная платформа — OpenWrt, а не Ubuntu. Приложение состоит из shell-скриптов,
статической панели HTML/JS/CSS и CGI под uhttpd; отдельной сборки, lockfile и
исходной автоматической тестовой системы нет.

| Компонент | Что делает | Связь с PPTP |
| --- | --- | --- |
| `roadwarrior-installer.sh` | OpenVPN-сервер, PKI, профиль клиента, LuCI, firewall, management routing; Passwall опционален | Входящий OpenVPN сохраняется |
| `webui/frontend` | Панель, управление OpenVPN и узлами Passwall, сеть, диагностика | Добавлена отдельная вкладка PPTP |
| `webui/cgi-bin` | API панели; аутентификация через сессию LuCI/ubus | Добавлен API профилей PPTP с JSON POST |
| `dual-vpn-switcher.sh` | Переключает Passwall/OpenVPN, меняет fw4 и DNS, распознаёт `tun*` | При выбранном PPTP уступает управление его отдельному контроллеру |
| `upstream-monitor.sh` | Обнаруживает внешний `tun*`, вызывает `rw-fix` | При выбранном PPTP приостанавливается |
| `vpn-dns-monitor.sh`, `openvpn-hotplug` | Получают DNS из OpenVPN | Сохраняются для OpenVPN; PPTP получает DNS через netifd |
| `start-all.sh`, `universal-client-monitor.sh` | Запускают старый runtime и защищают доступ к управлению | Не являются обязательными для установки PPTP; старый client monitor содержит фиксированные WAN/gateway |
| `legacy`, `dist`, `vpnpatch.txt` | Исторические установщики, готовая старая упаковка, отдельный routing patch | Не используются для упаковки нового расширения |

Важное несоответствие исходного проекта: `rw-fix`, который создаёт рекомендуемый
RoadWarrior installer, очищает маршруты и перезапускает службы. Старый switcher
ожидает от него настройку таблицы `vpnout` и nftables `rwfix`. Поэтому интеграция
PPTP не опирается на этот неоднозначный контракт и не переопределяет его.
Стандартный `webui/install/install.sh` ожидает плоскую папку с frontend, CGI и
runtime-файлами; актуальные исходники в репозитории разнесены по каталогам.
Новый `install-plus.sh` устанавливает непосредственно из этой структуры.

## Что добавлено

- Кнопка «Скачать OpenVPN для устройства» на Dashboard и во вкладке PPTP.
  Она выдаёт входящий клиентский профиль после входа в LuCI. API ищет обычный
  файл `/root/*.ovpn` с CA текущего `openvpn.rw`, исключает симлинки, не выдаёт
  серверные конфиги и запрещает кеширование скачанного профиля.
- Схема подключения: устройство → входящий OpenVPN на VPS → выбранный PPTP
  или узел Passwall → интернет. При смене выхода клиентский OpenVPN-профиль
  остаётся прежним. Файл содержит клиентский ключ, поэтому храните его приватно;
  для одновременного доступа разных устройств нужны отдельные клиентские сертификаты.
- Несколько сохранённых PPTP-профилей: адрес, логин, пароль, DNS, MTU и автозапуск.
- Добавление, редактирование без повторного ввода пароля, удаление, подключение
  и отключение. Одновременно выбран один исходящий PPTP-профиль.
- Штатный `ppp-mod-pptp`/netifd с MPPE и проверкой фактического поднятого интерфейса.
  Ответ «подключение запрошено» не означает успешную аутентификацию.
- Отдельные IPv4-правила: таблица 201, приоритеты 104/105. Основной WAN-маршрут
  сохраняется, чтобы не увести SSH, LuCI и транспорт входящего OpenVPN в PPTP.
- Для трафика, входящего с `openvpn.rw.dev` (обычно `tun0`), маршрутизация через
  PPTP и NAT. При выбранном, но недоступном туннеле сохраняются unreachable route
  и firewall guard. IPv6 этого клиентского трафика блокируется: PPTP-режим IPv4.
- DNS привязан к интерфейсу PPTP. После намеренного отключения восстанавливаются
  прежние DNS-настройки, если пользователь не изменил их во время подключения.
- Обработка событий netifd и отдельный monitor через procd. Выбор OpenVPN или
  Passwall в панели освобождает PPTP-режим; сервер OpenVPN `rw` не останавливается.
- Пароли хранятся в приватном `/etc/config/network`; API их не возвращает.
- Актуальные LuCI/rpcd-сессии принимаются по правам записи UCI `network` и
  `openvpn`; сессия только с правами чтения не даёт доступа к административному API.

Это добавление исходящего способа подключения. OpenVPN, Passwall и их протоколы
не заменяются. Проверка работоспособности исходных legacy-установщиков и всех
протоколов Passwall не входит в проверку PPTP-расширения.

## Требования и установка на OpenWrt

Поддерживаемая исходная платформа: OpenWrt 24.10 с opkg, работающим сервером
`openvpn.rw` и firewall zone `vpn` из RoadWarrior installer. Нужны ядро с PPP,
PPTP/GRE и MPPE, `/dev/ppp`, TCP 1723 и IP-протокол GRE (47) до PPTP-сервера.
Открытый TCP-порт сам по себе не доказывает, что GRE проходит.

На уже установленном роутере загрузите подготовленный архив через SCP/WinSCP,
распакуйте и выполните:

```sh
mkdir -p /root/router-plus-source
tar -xzf router-plus.tar.gz -C /root/router-plus-source
cd /root/router-plus-source
sh webui/install/install-plus.sh
```

Для свежего OpenWrt сначала запустите имеющийся `roadwarrior-installer.sh`.
Расширение не меняет существующие PKI, профили OpenVPN, узлы Passwall и SSH.
Перед обновлением панели и runtime сохраняется приватная резервная копия.
Если старые runtime-мониторы уже запущены, их нужно перезапустить, чтобы они
загрузили обновлённый код. Автозапуск нового PPTP monitor устанавливается отдельно.

Откройте `/cgi-bin/luci/admin/router_plus?page=pptp`, войдите через LuCI,
создайте профиль и нажмите
«Подключить». Реальные тестовые пароли вводите только в панель; в исходниках,
документации и архиве они не содержатся. Для редактирования сохранённого пароля
оставьте поле пустым. Изменения профиля вступают в силу после переподключения.

## VPS с Ubuntu 24.04

В пакетных настройках PPTP встречается строка `mppe required,no40,no56,stateless`,
которую `pppd 2.5.1` отклоняет с `OPTION_ERROR`. Установщик исправляет именно
этот стандартный вариант на `require-mppe-128`, `nomppe-40`, `nomppe-stateful`.
Обязательное 128-битное MPPE сохраняется. Перед заменой выполняется настоящий
`pppd dryrun` с PPTP plugin; исходный файл сохраняется в приватную резервную
копию. Другие строки сохраняются, а ошибка проверки оставляет исходный файл
без изменений. На уже работающем роутере достаточно выполнить
`sh webui/install/fix-pptp-options.sh` внутри OpenWrt, затем отключить и повторно
подключить выбранный PPTP-профиль. Ключи и данные профиля менять не требуется.

Установка OpenWrt-скриптов прямо в Ubuntu не поддерживается: там нет UCI,
netifd, procd и fw4. Нужен отдельный OpenWrt guest или контейнер. При контейнерном
варианте он использует ядро Ubuntu; установки OpenWrt kmod-пакетов недостаточно.
На хосте должны работать PPP, PPTP, MPPE, TUN и GRE, а контейнеру нужны NET_ADMIN
и доступ к `/dev/ppp` и `/dev/net/tun`. GRE через NAT требует отдельной проверки.

Перед развёртыванием на VPS проверьте его возможности:

```sh
uname -r
command -v docker
test -c /dev/kvm && echo KVM_available
sudo modprobe ppp_generic ppp_mppe pptp tun
test -c /dev/ppp && echo PPP_available
test -c /dev/net/tun && echo TUN_available
```

В архив включён read-only отчёт `deployment/check-ubuntu.sh`. Его можно запустить
через PuTTY и передать результат для проверки возможностей VPS; он не выводит
пароли. После подтверждения поддержки модулей доступен отдельный установщик:

```sh
cd /root/router-plus-source
sh deployment/check-ubuntu.sh
# После проверки отчёта и свободных портов:
SERVER_ADDRESS=144.172.99.28 bash deployment/install-ubuntu.sh
docker logs -f router-plus
```

Он создаёт OpenWrt-контейнер с отдельной сетью, приватными Docker volumes для
`/etc` и `/root`, входящим OpenVPN на UDP 1194 и панелью только на loopback 8080.
Правило PPTP conntrack ограничено исходящими соединениями этого контейнера;
модули и правило восстанавливаются при загрузке Ubuntu. Существующее развёртывание
с теми же именами и занятые порты вызывают остановку, а не замену данных.
Смена ОС и маршрутов хоста не выполняется. Установка Docker и kernel modules,
открытие UDP 1194 и создание проекта выполняются только при запуске этого
установщика пользователем на целевом VPS.

Firewall контейнера пропускает HTTP панели от Docker bridge gateway, через
который приходит SSH tunnel хоста. Ubuntu публикует этот порт только на loopback.
Установщик также загружает host-модули nftables, необходимые для fw4, и runtime
проверяет наличие загруженной таблицы fw4 перед сообщением об успешном старте.
Перед запуском сети также включается локальный `logd`. Если минимальный rootfs
не содержит `/etc/config/system`, создаётся минимальный конфиг с буфером журнала;
существующий конфиг сохраняется. `logread` показывает причины ошибок PPP/netifd.

Для панели в PuTTY настройте SSH tunnel: Source port `8080`, Destination
`127.0.0.1:8080`, Local. Откройте панель на своём компьютере через этот tunnel.
Адрес входа: `http://127.0.0.1:8080/cgi-bin/luci/admin/router_plus?page=pptp`.
LuCI ограничивает собственную cookie путём `/cgi-bin/luci/`. Новый вход выдаёт
отдельную HttpOnly/SameSite=Strict cookie для `/cgi-bin/vektort13`, только после
проверки прав записи `network` и `openvpn`. Сессия остаётся той же: выход из LuCI
и истечение срока сессии закрывают доступ к панели. При прямом открытии панели
без действующей cookie браузер переходит к этому входу.
Пароль роутера хранится внутри контейнера в приватном
`/root/roadwarrior-credentials.txt`, если установщик создал его автоматически.
Клиентский профиль OpenVPN можно получить командой:

```sh
docker cp router-plus:/root/client1.ovpn /root/client1.ovpn
chmod 600 /root/client1.ovpn
```

Либо после входа в LuCI скачайте его кнопкой «Скачать OpenVPN для устройства»
на Dashboard или во вкладке PPTP. Раздел OpenVPN с загрузкой upstream-конфигов
управляет исходящими соединениями и сохраняет исходное назначение.

Passwall feeds на свежем контейнере автоматически не устанавливаются: это
опциональный компонент исходного RoadWarrior installer. Исходная поддержка
Passwall в панели и runtime сохранена, существующие OpenWrt-развёртывания его
не теряют. Если он нужен на свежем контейнере, требуется отдельно установить
официальные Passwall feeds и GUI, затем проверить выбранный узел.

Для обновления только панели на уже работающем VPS распакуйте свежий исходный
архив в отдельный каталог (GitHub-архив требует `--strip-components=1`) и выполните:

```sh
bash /root/router-plus-update/deployment/update-panel.sh
```

Скрипт проверяет ownership label и работающий контейнер, сохраняет приватные
копии исходников панели и установленных файлов, обновляет `/opt/router-plus/webui`
для следующих запусков и устанавливает панель с LuCI-маршрутом. Перезапускается
только uhttpd; OpenVPN, PPTP, PKI, UCI-профили и Docker volumes сохраняются.

Проверки и сборка образа не заменяют испытания на VPS. Готовность Ubuntu-хоста и
реального PPTP-туннеля нельзя установить только по успешному входу через PuTTY.

## Проверка результата

Локальная проверка расширения:

```sh
python3 -m unittest discover -s tests -v
```

Она требует Docker и запускает изолированный настоящий OpenWrt rootfs,
CGI, ubus/rpcd и UCI. Проверяет аутентификацию, CRUD, сохранение пароля,
валидацию, отсутствие выполнения переданного shell-текста и kernel routing
при появлении/исчезновении тестового интерфейса. Тестовый интерфейс заменяет
внешний PPTP-сервер только в проверке маршрутов; это не тест PPP-аутентификации.

На настоящем роутере дополнительно обязательны:

1. После подключения `ubus call network.interface.<id> status` показывает `up`
   и `l3_device`; в панели статус «Подключён».
2. У клиента входящего OpenVPN внешний IPv4 соответствует выходу PPTP;
   DNS проходит через PPTP. SSH и исходный OpenVPN-сервер остаются доступными.
3. При обрыве PPTP клиент не получает выход через WAN и не использует IPv6
   в обход туннеля. Затем проверяются переподключение и восстановление DNS.
4. Переключение обратно на OpenVPN и Passwall работает; перезагрузка сохраняет
   профили и запускает только отмеченный для автозапуска PPTP-профиль.

Имя сервера разрешается в IPv4 перед подключением. Полученный адрес сохраняется
для повторных попыток native PPP после обрыва, когда туннельный DNS недоступен.
Если адрес сервера изменился, переподключите профиль при доступном DNS.
В выбранном PPTP-режиме firewall также блокирует исходящий DNS на WAN.

## Что проверено в облачной среде

- Двенадцать интеграционных проверок на OpenWrt 24.10.2 проходят: CGI/сессии ubus,
  CRUD, валидация, сохранение пароля, восстановление DNS, остановка напрямую
  запущенного OpenVPN-клиента, кеширование адреса сервера, маршруты/nftables при
  обрыве, приватное скачивание входящего OpenVPN-профиля и установка расширения.
  Отдельная проверка выполняет настоящий HTTP-вход LuCI с CookieJar: учитывает
  область действия cookie, переход в панель, сохранение профиля и запрет после
  logout. Вход в панель с правами только на чтение отклоняется.
  Проверка PPP воспроизводит `unrecognized option 'mppe'`, затем подтверждает
  принятие исправленных параметров реальным `pppd dryrun`, сохранение других
  опций, повторный запуск и сохранение исходного файла при ошибке проверки.
- Выполнена DOM-проверка вкладки через jsdom с настоящим CGI: навигация,
  добавление/редактирование/удаление и вывод имени как текста. Это не проверка
  внешнего вида в браузере. Chromium скачать не удалось из-за сетевого ограничения.
- Образ `deployment/Dockerfile` собирается. В отдельном контейнерном fixture
  дополнительно проверены генерация PKI исходным установщиком, настоящий OpenVPN
  `tun0`, вход root через rpcd, native uhttpd и скачивание профиля через порт хоста.
  Облако поддерживает TUN после создания device node, но PPP-устройство ядром
  не обслуживается. Поэтому PPP/GRE-аутентификация не проверена.
- Полный fw4 с REJECT в облаке требует отсутствующего kernel-модуля. Правило
  доступа к панели проверено с DROP-политиками и удалённой неиспользуемой REJECT
  цепочкой только в изолированном fixture. Production-политики не ослаблены;
  Ubuntu installer загружает необходимые native-модули хоста.
- Проверки не включают все исходные протоколы Passwall. Пользователь установил
  роутер на Ubuntu 24.04 через PuTTY: журналы подтвердили работающий OpenVPN,
  созданный клиентский профиль, PPTP-расширение и успешный запуск службы host
  conntrack helper. Панель открывается через SSH tunnel. Прямой SSH из облака
  остаётся недоступен. Реальные PPTP/GRE и выход устройства через OpenVPN ещё
  требуют проверки на VPS.

PPTP применяется для совместимости с существующими серверами; это устаревший
протокол, который не следует считать современным защищённым VPN.
